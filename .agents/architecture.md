# Architecture guidance

Each section names the file that holds the truth. When this doc and that file disagree, the file wins — fix this doc.

## Where code lives

The workspace list in the root `package.json` (`workspaces`) is the authoritative map. In short:

- `components/<Name>/` — reusable UI used across 2+ Cypress products. Each framework or constants folder is its own npm package. Ship React and Vue unless there's a reason not to; check the folder for which ones a component has.
- `packages/` — build tools and utilities used by components but not components themselves (ESLint plugin, Tailwind/rollup plugins, color constants).
- `css/` — `@cypress-design/css`, the design tokens.
- `icon-registry/` — icon SVGs and the generator for the icon types.
- `docs/` — the Astro site deployed to `design.cypress.io`.

Scaffold a new component with `yarn new:component` (templates in `_templates/component/`), then follow `skill(implement-component)`.

## Docs demos

- Live examples live in `docs/src/demos/`. `docs/src/pages/components/[component].astro` renders them; read it for how a page picks its layout.
- Tile-based pages use `docs/src/demos/<Name>/`: `tiles.ts` sets the order, `vue/<Tile>.vue` and `react/<Tile>.tsx` hold one self-contained example each (shown verbatim as the tile's code), and an optional `AllStates.{vue,astro,tsx}` is the gallery under the page title. Tiles missing a framework are listed in `docs/src/demos/MISSING.md`.
- Tile code is editable in the browser (`docs/src/lib/tile-editor.ts`). Its imports resolve through `docs/src/lib/tile-modules.ts` — register every new component package there, or editing its tiles fails with "The editor can't import …".
- New tiles reuse the sample data, labels, and placeholders from the component's existing demo. Only write new data when no existing example covers the feature.

**When adding component docs:** write `components/<Name>/instructions.md`, add tiles under `docs/src/demos/<Name>/`, register the package in `tile-modules.ts`, and add the component to the list in `.agents/index.md`.

## Styling

**Use Tailwind for all styling** — no SASS, CSS Modules, or CSS-in-JS. Tokens come from `tailwind.config.mjs`; reach for one before an arbitrary value.

Tooling flags class problems but doesn't fail CI:

- Prettier (`.prettierrc.json`) sorts classes; the pre-commit hook runs it on staged files. Don't hand-order classes, and don't reorder `twMerge()` arguments — the last conflicting class wins, so their order matters.
- ESLint (`eslint.config.js`) warns on arbitrary values and unknown classes. A legitimate non-Tailwind hook class goes in that file's `whitelist`, not an inline disable. Read the config for which files each rule covers.

**Don't write new WindiCSS.** The `WindiColor` type (generated by `icon-registry/generate-icons-content.mjs`) still leaks into icon props; use static strings or casts in calling code rather than spreading the type.

## Building and running

- Yarn version: `packageManager` in `package.json`. Setup steps, including fixing a global Yarn 1 shadowing Corepack, are in `ReadMe.md` under "Set up Node and Yarn".
- Scripts: the root `package.json` `scripts`. The usual ones are `yarn dev` (watchers + Astro dev server) and `yarn build:docs`.
- CI: `.github/workflows/`.

### Gotcha: editing source doesn't change what consumers see

Every component package's `exports` point at its built `dist/`, not its source. The docs site and any linked consumer import `dist/`, so if `yarn dev`'s watchers aren't covering a package, a source edit has **no visible effect** until it's rebuilt. That looks exactly like "the fix didn't work".

Check by comparing modification times of `dist/` and your edited file (`ls -lt`). To rebuild one package, run its `build` script (`yarn workspace <package name> run build`) — React packages build with rollup, Vue packages with Vite; see the package's own `package.json`. If a `yarn run` script can't find its binary, run it from the repo root's `node_modules/.bin/`. Confirm `dist/` is newer before saying a change is live.

## Publishing

Packages publish to npm through Changesets: add a `.changeset/*.md` intent file with your change (see `.changeset/README.md`; config in `.changeset/config.json`). The site deploys to `design.cypress.io` via Vercel (`vercel.json`) from `main`.

An `@cypress-design/*` package in a published package's `dependencies` must use `workspace:^<its current version>`, so a major release of a dependency republishes its dependents. `scripts/check-internal-deps.mjs` enforces this in PR CI (its header explains why), and `scripts/changesets-workspace-ranges.test.mjs` holds Changesets to it. Because Changesets rewrites those ranges, the `version-packages` script also updates `yarn.lock` — keep that step, or the version PR fails `yarn install --immutable` (PR #722). `yarn release` resolves `workspace:` ranges to plain semver (`scripts/set-version.mjs`) before publishing.

## Hosted styles

`yarn workspace @cypress-design/css build:colors-css` (`css/src/generate-colors-css.ts`) writes `colors.css` and `tokens.css` into `docs/public/`, so build-free consumers can load them from `https://design.cypress.io/colors.css` and `https://design.cypress.io/tokens.css`.
